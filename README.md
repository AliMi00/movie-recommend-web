# CineJo Web

A Flutter Web client for a movie recommendation API, containerised and
deployed to a self-hosted homelab with Terraform, Traefik, GitHub Actions
and a Prometheus/Grafana stack.

**Live demo: [demo1.mobini.nl](https://demo1.mobini.nl)** — a shared demo
account is offered on the sign-in screen, or register your own.

> The focus of this repository is the **infrastructure and delivery
> pipeline**. The application is an existing Flutter app of mine, adapted to
> run as a web build; the recommendation engine that powers it is a separate
> private service and is **not** part of this repository.

## Architecture

```
                    ┌────────────────────────────────────────────┐
   Browser ────────▶│  VPS (public edge)                         │
   HTTPS            │    Caddy — TLS termination                 │
                    └──────────────────┬─────────────────────────┘
                                       │ Tailscale (private mesh)
                                       ▼
                    ┌────────────────────────────────────────────┐
                    │  Homelab host — Docker                     │
                    │                                            │
                    │   Traefik :8060 ──────┐                    │
                    │     routing, metrics  │                    │
                    │                       ▼                    │
                    │   nginx  :8080  (Flutter Web static build) │
                    │     ├── /healthz                           │
                    │     └── :9113 stub_status                  │
                    │              │                             │
                    │   nginx-exporter :8062                     │
                    │   Prometheus     :8064 ◀── scrapes both    │
                    │   Grafana        :8065                     │
                    └──────────────────┬─────────────────────────┘
                                       │
                       browser calls   │  (direct, not proxied)
                                       ▼
                    ┌────────────────────────────────────────────┐
                    │  CineJo API — api.gozaga.xyz               │
                    │    ┌────────────────────────────────────┐  │
                    │    │  Recommendation engine             │  │
                    │    │  PRIVATE — not part of this repo   │  │
                    │    └────────────────────────────────────┘  │
                    └────────────────────────────────────────────┘
```

The browser talks to the API **directly** rather than through this app's
nginx. The client is a static bundle; proxying API traffic through it would
add a hop, hide the real client IP from the API's rate limiting, and make
this container a dependency of every API call. CORS on the API allows the
demo origin instead.

### Delivery pipeline

```
push to main ──▶ CI ── format, analyze, test, build image, smoke-test it
                  │ on success
                  ▼
             Release ──▶ ghcr.io/…/cinejo-web:<sha> + :latest
                                    │
                    poll every 5m   │   outbound only — nothing reaches in
                                    ▼
                        deploy agent on the homelab
                          pull → digest changed? → terraform apply → verify
```

## Why each piece

**Docker, multi-stage.** The build stage needs the Flutter SDK (~1GB); the
runtime needs a web server and a folder of static files. A multi-stage build
keeps the SDK out of the shipped image — 143MB of nginx-alpine and compiled
assets rather than a build environment in production.

**nginx over a Dart/Node server.** The output of `flutter build web` is
static files. nginx serves those, handles gzip, sets cache headers, and
provides the SPA fallback that client-side routing needs. It runs as a
non-root user on port 8080.

**Runtime config injection, not build-time.** Flutter Web compiles to static
JS and cannot read environment variables. Baking the API URL in at compile
time would mean a separate image per environment. Instead `index.html` ships
with placeholders that the container entrypoint substitutes at startup, and
Dart reads them back through JS interop. One image, promoted unchanged.

**Terraform over shell scripts.** The deployment is a network, five
containers, two volumes and a routing table. Terraform makes that state
declarative and diffable: `terraform plan` shows exactly what a change will
do before it happens, and the same config reproduces the stack from nothing.

**Traefik with the file provider.** Traefik gives per-service request rate
and latency histograms that nginx's `stub_status` cannot express. Routing is
declared in a config file generated by Terraform rather than discovered from
Docker labels — that avoids mounting the Docker socket into an
internet-facing proxy, which would turn any compromise of it into
root-equivalent control of the host. (It also sidesteps a real incompatibility:
Traefik's Docker provider negotiates API version 1.24, which Docker 25+
daemons reject.)

**TLS at the VPS, not at Traefik.** The homelab has no public ingress; a VPS
terminates HTTPS and forwards over Tailscale. A second certificate at Traefik
would be redundant and would require exposing the homelab directly.

**GitHub Actions for CI, a pull agent for CD.** See below — this is the most
deliberate decision in the project.

**Prometheus + Grafana.** A healthcheck answers "is it up right now".
Prometheus answers "was it slow at 3am, and for whom". Traefik supplies
status codes and latency percentiles; the nginx exporter supplies connection
state; the dashboard is committed as JSON and provisioned automatically, so
it is reproducible rather than hand-built in a UI.

### The deployment direction

The homelab accepts SSH only from a private tailnet. Deploying *from* CI
would require one of:

- an SSH key plus tailnet access stored in GitHub secrets — a credentialed
  route into a home network, held by a third party; or
- a self-hosted runner — worse on a **public** repository, where a pull
  request from a fork can execute arbitrary code on the runner, inside the
  network.

Inverting the direction removes the problem instead of mitigating it. CI's
responsibility ends at publishing an image. A systemd timer on the homelab
polls GHCR, compares the pulled digest against what is running, and applies
only when they differ. There is no inbound firewall rule, no long-lived
credential outside the host, and nothing to revoke if this repository is
compromised.

The cost is latency: a release reaches production on the next poll rather
than instantly. For a portfolio demo that is a trade worth making, and it is
the same pattern GitOps controllers such as Flux and Argo CD use for
precisely this reason.

## Running it locally

Requires Docker. Nothing else — the image builds Flutter itself.

```bash
cp .env.example .env      # optional; defaults point at the public API
docker compose up -d --build
```

Then open <http://localhost:8060>.

To work on the app with hot reload instead, you need the Flutter SDK
(3.32.8):

```bash
flutter pub get
flutter run -d chrome --dart-define=CINEJO_API_BASE_URL=https://api.gozaga.xyz/v1
```

### Checks

```bash
dart format --output=none --set-exit-if-changed lib test
flutter analyze --fatal-infos
flutter test
```

These are exactly what CI runs.

## Deploying

Full setup, Terraform state ownership and rollback: **[deploy/README.md](deploy/README.md)**.

Short version — on the deployment host:

```bash
sudo install -d -m 700 /etc/cinejo-web
sudo install -m 600 deploy/agent/deploy.env.example /etc/cinejo-web/deploy.env
sudo "$EDITOR" /etc/cinejo-web/deploy.env
sudo install -m 755 deploy/agent/cinejo-deploy.sh /usr/local/bin/cinejo-deploy.sh
sudo install -m 644 deploy/agent/cinejo-deploy.{service,timer} /etc/systemd/system/
sudo systemctl enable --now cinejo-deploy.timer
```

Terraform can also be applied directly for the initial bootstrap:

```bash
cd terraform
cp terraform.tfvars.example terraform.tfvars   # fill in; gitignored
terraform init && terraform apply
```

No hostname, IP or credential is committed. Everything
environment-specific comes from `terraform.tfvars` or `TF_VAR_*`.

### Observability

| Endpoint | Purpose |
|---|---|
| `/healthz` | Liveness. Served by nginx with no API dependency, so an API outage does not mark the web tier unhealthy. |
| `:8062/metrics` | nginx connection and request counters. |
| `:8063/metrics` | Traefik request rate, status codes, latency histograms. |
| `:8064` | Prometheus. |
| `:8065/d/cinejo-web` | Grafana — the **CineJo Web** dashboard, auto-provisioned. |

Metrics ports are bound to the private network and are deliberately not
routed through Traefik.

## Security notes

- No secrets in the repository. `.env.example` and
  `terraform.tfvars.example` hold placeholders only; real values live in
  gitignored files or `TF_VAR_*`.
- The container runs as a non-root user with `no-new-privileges`.
- The Docker socket is **not** mounted into any internet-facing container.
- A Content-Security-Policy is applied to every response. It is deliberately
  narrow, and the two third-party origins it does allow
  (`fonts.gstatic.com`, `image.tmdb.org`) are documented in
  `nginx/security-headers.conf` with the reason each is required — both are
  fetched by `fetch()`/XHR under CanvasKit, so they need `connect-src`, not
  just `font-src`/`img-src`.
- The recommendation engine and all backend logic stay in a separate private
  service. This repository only calls the public API surface, which is
  documented in `openapi.json`.

## What this project demonstrates

For anyone reviewing this as work product:

- **Adapting an existing codebase**, not greenfield work — taking a
  Flutter app that targeted mobile and making it a deployable web artifact:
  removing platform-specific dependencies, fixing routing for real URLs, and
  handling a layout built for phone widths on desktop viewports.
- **Containerisation with intent** — multi-stage builds, non-root runtime,
  small images, healthchecks, and the build-once/run-anywhere config pattern
  that keeps one artifact promotable across environments.
- **Infrastructure as code** — a declarative, reproducible deployment with
  no hardcoded environment values, where changes are reviewed as a diff
  before they are applied.
- **Threat-modelled delivery design** — choosing a pull-based deployment
  because the push-based alternatives required handing a third party a route
  into a private network, and being explicit about the trade-off that
  choice costs.
- **Observability that answers questions** — knowing the difference between
  a healthcheck and a time series, choosing metrics that survive contact
  with a real incident (latency percentiles over averages, error *ratio*
  over error count), and committing the dashboard as code.
- **Debugging what actually happens rather than what should** — several
  defects in this repository's history were caught only by exercising the
  running system in a browser: nginx silently dropping security headers
  through `add_header` inheritance, a Content-Security-Policy that rendered
  the entire UI textless, and a Traefik deployment that applied cleanly
  while serving nothing but 404s. Each is documented at the point of the fix.
